# eztaiji 동작·상태 데이터 모델

- 설계 버전은 `0.1`이다. 기존 앱에 적용하기 전의 설계 기준이다.
- 검토 기준은 저장소 커밋 `81b9ccbfadfeefb779e419b993ec0749b7d041e5`이다.
- 이번 범위는 모델, 화면과의 계약, 이행 순서, 설계 시험이다. 기존 예비식 데이터와 배포 화면은 아직 바꾸지 않는다.
- 이 문서는 프로젝트의 표기·개발 규칙을 제안한다. 易簡太極拳의 공식 기술 정의나 실연 검증 결과가 아니다.

## 1. 핵심 결정

**권가의 순서, 몸의 상태, 상태 사이의 움직임, 그 움직임에 대한 해석, 화면 구성을 분리한다.**

`권가 순서 → 동작 → 시작·중간·결과 상태`가 움직임의 골격이다. 설명과 음양·전투 가정은 이 골격의 특정 범위를 참조한다. 화면은 이 정보를 조합해 보여주며, 화면을 그리기 편하도록 수련 데이터를 바꾸지 않는다.

예를 들어 앞 자세의 마지막 화면과 다음 자세의 시작 화면은 같은 몸 상태를 가리킬 수 있다. 그러나 제목, 설명, 보여줄 변화, 관련 용법은 서로 다르다. **상태 공유는 화면 전체의 복사를 뜻하지 않는다.**

## 2. 현재 구현에서 확인한 한계

| --- | --- | --- |

| B는 언제나 정면으로 그린다. | 몸 방향과 회전 경로를 설명할 수 없다. | 현재 B는 상태에, 회전 과정은 동작에 기록한다. |

이 한계는 예비식 시제품의 잘못이라기보다, 예비식에 한정된 가정이 코드에 들어가 있다는 뜻이다.

## 3. 권가의 단위와 식별자

| 단위 | 책임 |
| --- | --- |
| `Dataset` | 선택한 수련 기록·자료 체계와 스키마 버전을 정한다. |
| `Section` | 단의 순서와 소속 자세를 정한다. |
| `PostureOccurrence` | 권가의 그 위치에서 등장하는 자세를 나타낸다. |
| `Motion` | 원자료의 번호가 붙은 한 동작을 나타낸다. |
| `State` | 특정 시점에 기록된 몸 상태를 나타낸다. |
| `Interpretation` | 원리·음양·전투 가정을 특정 범위에 연결한다. |
| `Source` | 문헌·영상·수련 메모·기존 코드 등의 근거를 식별한다. |

`PostureOccurrence`를 쓰는 이유는 같은 이름의 자세가 여러 번 등장하기 때문이다. 1단의 單鞭과 뒤에 나오는 單鞭은 이름이 같아도 별개의 항목이다. 시작 상태와 연결 문맥을 이름으로 재사용하지 않는다.

ID는 이름이나 배열 인덱스와 분리한다. 예를 들어 `p001`, `p001-m01`, `p001-m01-end`, `p003-g-left-peng`처럼 안정된 ID를 쓴다. 번호는 표시·원자료 대조용이며, 이름의 오탈자를 고쳐도 참조 ID는 바뀌지 않는다. 서로 다른 Dataset 사이의 참조는 이번 버전에서 허용하지 않는다.

저장 문서의 최상위에는 `schemaVersion`, `id`, `revision`, `coordinateFrames`, `sections`, `postures`, `motions`, `states`, `groups`, `interpretations`, `sources`를 둔다. `sections[].postureIds`를 펼치면 권가 전체 순서가 나온다. 아래 설계 시험의 `postureIds`는 이 파생 순서를 단순화한 입력이다. 중복된 순서표를 따로 편집하지 않는다.

`CoordinateFrame`에는 ID, 기준 시점·원점 설명, 축 정의, 단위를 둔다. `PostureOccurrence`에는 ID, 표시 번호·이름, 시작 참조, `motionIds`, 자세 소개를 둔다. 알 수 없는 스키마 버전은 조용히 해석하지 않고 명시적으로 거부한다. 내용 교정의 `revision`과 저장 형식의 `schemaVersion`은 별개다.

한 자세의 `motionIds`는 원자료 순서대로 둔다. 내용이 미등록이어도 동작 슬롯은 존재할 수 있다. 총 동작 수는 이 슬롯을 세며, 시작 상태·중간 상태·해석은 세지 않는다. 현재 프로젝트 목차의 64자세·365동작은 대조용 기대값이지 렌더러의 고정 상수가 아니다.

묶음은 이름과 명시적인 `motionIds`를 가진다. 左掤이라는 이름만 저장하거나 시작 번호와 개수를 여러 곳에 중복 저장하지 않는다. 그룹 설명과 임의의 일부 동작에 걸친 설명을 혼동하지 않는다.

## 4. 상태와 움직임의 경계

### 4.1 상태는 ‘지금 어떠한가’를 기록한다.

`State`에는 발 위치, 발 방향, 발별 지지 역할, 현재 접촉, 중심 C, 몸 방향 B, 필요한 팔의 상대적 배치를 담는다. 상태는 완성된 관측 항목 묶음이다. 빠진 값을 직전 상태에서 몰래 상속하는 변경분 방식은 사용하지 않는다.

### 4.2 동작은 ‘어떻게 변했는가’를 기록한다.

`Motion`은 결과 상태를 가리키고, 필요한 경우 중간 상태와 사건을 가진다. 출발 상태는 자세의 시작 상태 또는 바로 앞 동작의 결과에서 구한다. 출발 상태를 별도 사본으로 저장하지 않는다.

```text
Motion
  id, number
  endStateId                 # 결과 상태가 미등록이면 null이다.
  checkpointStateIds[]       # 확인된 순서의 중간 상태만 둔다.
  events[]                   # 들기·내리기·이동·회전 같은 변화를 둔다.
  eventRelations[]           # 확인된 선후·겹침 관계만 둔다.
  instruction                # 출발점에서 결과까지의 안내이다.
  checks[]                   # 사용자가 몸으로 확인할 사항이다.
```

1동작의 좌표판은 기본적으로 결과 상태를 보여준다. 설명에는 변화 과정을 담는다. 중간 단계가 있더라도 원자료의 1동작을 1·2·3동작으로 새로 세지 않는다. 필요하면 같은 동작 안에서 ‘과정 보기’로 펼친다.

`events` 배열 순서 자체는 시간 순서를 뜻하지 않는다. 먼저 일어났다는 근거가 있으면 `before`, 겹쳤으면 `overlaps`, 동시성이 확인되면 `simultaneous` 관계를 기록한다. 관계가 없으면 순서를 미확인으로 남긴다. 가상의 소요 시간이나 같은 간격의 타임스탬프는 만들지 않는다.

사건은 `id`, 대상(`leftFoot`, `rightFoot`, `body`, `center`, `leftArm`, `rightArm`), 종류, 설명의 Claim을 가진다. 필요한 경우 시작·중간·끝 중 어디에 걸치는지 `span`으로 명시한다. 회전량·경로가 확인된 사건만 해당 값을 가진다. 끝점만으로 이동 경로나 회전 방향을 복원하지 않는다.

### 4.3 상태와 사건은 다음처럼 다르다.

| 상태에 기록한다. | 사건에 기록한다. |
| --- | --- |
| 발끝이 닿아 있다. | 발끝을 처음 댄다. |
| 뒤꿈치가 들려 있다. | 뒤꿈치를 든다 / 내린다. |
| 오른발이 주로 지지한다. | 지지를 왼발에서 오른발로 옮긴다. |
| B가 오른쪽을 향한다. | 시계 방향으로 몸을 돌린다. |

`Heel ↑`와 `Heel ↓`는 사건에서 표시한다. 다음 자세의 시작 상태로 넘어가도 ‘뒤꿈치가 들려 있다’는 확인된 상태는 공유할 수 있지만, ‘지금 뒤꿈치를 든다’는 화살표를 다시 재생하지 않는다.

`ΔB` 역시 상태의 속성이 아니다. 0°에서 0°로 끝났다고 회전이 없었다고 판단하지 않는다. 끝점 차이는 계산값일 뿐 실제 회전 방향·횟수·경로의 증거가 아니다.

## 5. 시작 상태의 참조

```text
PostureOccurrence.start
  { kind: "initial", stateId }                  # 첫 자세에만 쓴다.
  또는
  { kind: "previousEnd", postureId }            # 바로 앞 자세를 명시한다.
```

`previousEnd`는 같은 Dataset에서 지정한 바로 앞 자세의 마지막 동작 결과를 가리킨다. 참조할 마지막 동작이 미등록이면 ‘이전 자세의 마지막 상태 미등록’으로 남긴다. 가장 가까운 등록 상태를 대신 가져오거나 숫자 0으로 채우지 않는다.

첫 자세의 초기 상태도 실제 값이 확인되지 않았다면 미확인이다. 예비식 1동작의 결과를 초기 상태로 복사하거나 권가의 마지막 자세와 자동 연결하지 않는다.

참조된 상태의 발·중심·몸 정보만 공유한다. 다음 자세의 소개, 관련 해석, 확인 사항은 다음 자세 문맥에서 선택한다. 공통 상태가 수정되면 이를 참조하는 시작 화면도 바뀌어야 한다. 사본을 따로 수정하는 방식은 금지한다.

개별 동작의 미등록 `endStateId`는 정상적인 자료 공백이다. 존재하지 않는 ID나 순환 참조는 데이터 오류이다. 둘은 사용자와 작성자에게 다르게 보고한다. 단독 발췌본이나 다른 수련 방식의 시작 상태는 기존 순서를 덮어쓰지 않고 향후 별도 Dataset으로 다룬다.

## 6. 사실·근사·미확인의 공통 형식

필드 하나하나가 같은 확실도를 가진다고 가정하지 않는다. 좌표는 설명용 근사이고 발 접촉은 자료에 명시된 정보인 경우를 그대로 표현해야 한다.

```ts
type EvidenceRef = {
  sourceId: string;
  locator: string;            // 동작 번호, 문단, 영상 시점, 메모 위치이다.
  support: "explicit" | "contextual";
};
type Claim<T> =
  | {
      status: "known";
      value: T;
      basis: "source" | "observation" | "inference" | "illustration";
      precision: "qualitative" | "approximate" | "measured";
      evidence: EvidenceRef[];
      note?: string;
    }
  | {
      status: "unknown";
      reason: "unrecorded" | "unverified" | "not_visible" | "conflicting";
      note?: string;
      evidence?: EvidenceRef[];
      alternatives?: { value: T; evidence: EvidenceRef[]; note?: string }[];
    }
  | { status: "not_applicable"; reason: string };
```

`known`은 값이 기록되었다는 뜻이지, 실제 동작이 검증되었다는 뜻이 아니다. `basis`와 근거를 함께 읽는다. `measured`는 측정 방법·대상·범위를 추적할 수 있을 때만 쓴다. 수치가 소수점이라고 측정값이 되는 것은 아니다.

`source`와 `observation`에는 근거가 필요하다. `inference`에는 근거와 추론 설명을 남긴다. `illustration`에는 학습용 예시라는 설명을 남기며, 실제 동작의 관찰로 승격하지 않는다. 스키마가 근거의 존재를 검사할 수는 있어도 그 근거가 실제 주장을 뒷받침하는지는 사람이 검토해야 한다.

`Source`에는 `id`, 자료 종류, 제목, 위치(URL 또는 저장소 경로), 필요한 기록 날짜를 둔다. 사부님 설명은 실제 메모의 위치를 근거로 삼는다. 중국어 설명을 확실히 이해하지 못한 기록은 검증된 지도 내용으로 표시하지 않는다. 외부 자료와 수련 기록이 다르면 `unknown/conflicting`과 `alternatives`에 각각의 값·근거를 보존한다. 마지막에 입력된 값을 자동 채택하거나 임의로 합쳐 하나의 사실처럼 만들지 않는다. `alternatives`는 충돌이 있을 때만 사용한다.

작성 도구는 물리 필드를 미확인으로 초기화하는 템플릿과 공통 Source 참조를 제공할 수 있다. 작성자가 매번 같은 근거 문구를 복사할 필요는 없다. 단, 템플릿이 빠진 값에 의미를 부여하거나 출처를 바꿔 붙이지는 않는다.

물리 필드의 미확인은 Claim으로 명시한다. `null`은 `endStateId`처럼 아직 연결할 자료가 없는 참조에만 사용한다. `0°`, `(0,0)`, 빈 문자열, 이전 값은 미확인의 대용품이 아니다. 지원하지 않는 스키마 필드나 빠진 필수 필드는 검증 오류로 구분한다.

콘텐츠의 작성 상태와 사실의 확실도도 다르다. 설명 카드는 `pending`, `present`, `not_applicable`로 준비 상태를 표시한다. `present`여도 내용의 Claim은 추론일 수 있다. ‘전투 가정 미작성’과 ‘검토 결과 이 단계는 독립 용법을 제시하지 않음’을 구분한다.

## 7. 신체 상태의 최소 구조

```text
State
  id, coordinateFrameId
  feet.left / feet.right
    position: Claim<{x, y}>
    heading: Claim<Direction>
    supportRole: Claim<"shi" | "xu" | "shared">
    groundContact: Claim<"toe" | "forefoot" | "heel" | "sole" | "none" | "other">
    heelRaised: Claim<boolean>
  center
    location: Claim<PointOrRegion>
  body
    heading: Claim<Direction>                   # 화면의 B이다.
    organization: Claim<string>                 # 필요할 때 질적으로 설명한다.
  arms.left / arms.right
    configuration: Claim<string>               # 몸과의 상대적 배치·역할을 설명한다.
```

`Direction`은 `{kind:"angle", degrees}` 또는 `{kind:"sector", sector}`이다. sector는 기준 정면에 대한 여덟 방향 이름이다. 대략 오른쪽 앞이라는 정보만 있으면 이를 정확한 45°로 저장하지 않는다. 도해에서 화살표를 45°로 그리더라도 범주를 보여주는 화면 표현일 뿐이다.

C는 `{kind:"point", x, y}` 또는 `{kind:"region", anchor:"leftFoot"|"rightFoot"|"betweenFeet"|"front"|"back"}`로 기록한다. ‘오른발 쪽’이라는 정보를 임의의 `x=0.87`로 바꾸지 않는다. 중심이 미확인이면 지지 역할에서 계산해 채우지 않는다.

`shi/xu/shared`는 발별 기록이다. `shared`는 이 앱의 ‘양발이 함께 지지함’이라는 기술용 값이지 전통 이론의 새 허실 범주나 ‘雙重’ 판정이 아니다. 비율은 뜻하지 않는다. 왼발을 實로 기록했다고 오른발을 자동으로 虛로 만들지 않는다.

`groundContact:none`은 확인된 비접촉이다. 미확인과 다르다. 虛인 발이 반드시 공중에 있다고 가정하지 않는다. 발끝 접촉, 뒤꿈치 접촉, 들기·내리기, 회전축도 서로 추론하지 않는다. Toe/Heel 접촉·사건 표시는 명시적 근거가 있는 source/observation Claim에만 허용한다. 추론은 해설에 남길 수 있지만 접촉 기호로 사실처럼 그리지 않는다.

팔은 처음부터 질적 설명을 담을 자리를 둔다. 손의 모양만으로 역할을 정하지 않으며, 자료에 없는 3차원 손 좌표는 만들지 않는다. 太極起勢처럼 발의 평면 위치가 변하지 않아도 팔·몸의 변화로 서로 다른 동작을 설명할 수 있어야 한다.

상승·하강은 우선 동작 사건과 설명으로 다룬다. C의 평면상 y에 높이 변화를 넣지 않는다. 골반·흉곽 방향의 별도 수치와 실제 높이 좌표는 이를 요구하는 검증된 사례가 생길 때 확장한다.

## 8. 좌표 기준과 화면 좌표

축은 太極起勢 종료 시점을 기준으로 고정한다. **+x는 그 기준 시점의 오른쪽이며, 몸이 돈 뒤의 현재 오른쪽이 아니다.** `leftFoot/rightFoot`는 몸의 해부학적 좌우이고, `B`는 고정 좌표 안에서의 방향이다.

다음은 기존 좌표계 1.2에서 모델 이행 전에 명확히 고쳐야 할 부분이다.

| 항목 | 새 모델의 결정 | 이행 시 주의할 점 |
| --- | --- | --- |
| 발 좌표의 기준점 | 발 형태 중심을 바닥 평면에 투영한 학습용 기준점으로 정의한다. | 기존 ‘접촉면 가운데’와 구분한다. 공중에 뜬 발에도 좌표를 줄 수 있어야 한다. 접촉점이나 회전축을 뜻하지 않는다. |
| C의 화면 위치 | 기록된 점 또는 질적 영역만 표현한다. | 기존 C의 세로 픽셀 오프셋을 실제 평면 좌표로 가져오지 않는다. |
| 단위 | 기준 자세의 양발 간격을 1로 하는 근사 단위를 유지한다. | 모든 실제 보폭이 반드시 같은 1이라고 강제하지 않는다. |
| 화면 이동 | 확대·축소·이동은 화면 변환으로만 처리한다. | 새 자세가 보이도록 화면을 옮겨도 저장된 원점을 다시 잡지 않는다. |

이 표는 설계 결정이며, 기존 좌표계 문서와 렌더러에 적용한 상태가 아니다. 예비식 마이그레이션 시작 전에 좌표계 문서를 갱신하고 기존 값의 의미를 다시 확인한다. 기존 근사 좌표를 새 기준점의 실측값인 것처럼 재분류하지 않는다.

같은 자세의 시작·중간·끝을 비교할 때는 같은 축·단위·화면 범위를 사용한다. 매 동작마다 자동으로 화면을 중심 맞춤하면 발이 움직였는지 화면이 움직였는지 헷갈릴 수 있다. 화면 범위 계산은 렌더러의 책임이며 State에 픽셀 좌표를 저장하지 않는다.

## 9. 음양·전투 해석의 연결 방식

해석을 State 안에 넣지 않는다. 같은 몸 상태도 앞뒤 동작이나 가정한 상대에 따라 의미가 달라질 수 있기 때문이다.

```text
Interpretation
  id
  category: principle | yinYang | application
  scope
    {kind:"motion", motionId}
    또는 {kind:"group", groupId, motionIds?}
    또는 {kind:"posture", postureId}
  availability: pending | present | not_applicable
  content                                    # present일 때만 둔다.
  reason                                     # 미작성/비적용 이유를 둔다.
```

부분 묶음의 `motionIds`는 해당 그룹 안에서 실제로 선택한 연속 범위를 명시한다. 예를 들어 左掤 전체와 左掤 중 1–3동작은 다른 범위이다. 같은 이름의 다른 자세나 다른 Dataset으로 범위를 넘기지 않는다.

음양 내용은 `terms`, 두 측면의 구체적인 작용, 그 둘이 연결되는 방식의 Claim을 담는다. 필드 이름을 영구적인 `yinFoot/yangFoot`로 두지 않는다. ‘左虛 ↔ 右實’은 특정 시점의 해석이며 몸의 고정 속성이 아니다. 전통적 대립쌍과 프로젝트의 설명용 대비는 작성 원칙에서 구분한다. ‘進 ↔ 化’를 표준 음양 분류로 자동 등록하지 않는다.

전투 가정은 `assumption`, `response`, `possibleResult`, `limitations`의 Claim을 담는다. 상대의 접촉·힘 방향·거리 같은 전제가 빠져 있다면 결과를 단정하지 않는다. 독립 용법과 다음 움직임의 준비 구조를 구분한다. 여러 가정이 있으면 별개의 해석으로 보존하며 하나의 확정 용법으로 섞지 않는다.

가정된 상대는 실제 수련자의 State에 넣지 않는다. 이번 버전의 좌표판에는 상대나 힘 벡터를 자동으로 그리지 않는다. 추후 추가하더라도 별도의 ‘가정 보기’ 계층이어야 한다. 이번 설계는 음양·전투 콘텐츠의 저장 자리를 정하며, 각 동작의 실제 해석 검증을 완료한 것은 아니다.

## 10. UI에 전달할 계약

화면 선택은 `{postureId, view:"start"}` 또는 `{postureId, view:"motion", motionId, checkpointStateId?}`로 관리한다. 내부 배열의 0번과 화면의 ‘0동작’을 혼동하지 않는다. 선택·접힘·스크롤 위치는 UI 상태이며 수련 데이터에 넣지 않는다.

화면에 건네는 정보는 다음 순서로 조합한다.

1. 선택한 자세와 동작을 권가 순서에서 찾는다.
2. 시작·현재·결과 상태 참조를 해석한다.
3. 같은 좌표계인지, 어떤 물리 정보가 표시 가능한지 확인한다.
4. 해당 화면의 설명과 범위가 맞는 해석을 모은다.
5. 표시하는 Claim의 근거만 모아 전달한다.

| 데이터 상황 | 화면의 동작 |
| --- | --- |
| 다음 자세의 시작 상태이다. | 같은 몸 상태를 보여주되 다음 자세 소개를 쓴다. 이전 동작의 사건 화살표는 제거한다. |
| 좌표는 없고 설명은 있다. | 설명을 보여주고 좌표 미등록을 알린다. 화면 전체를 준비 중으로 막지 않는다. |
| 발 위치는 있고 허실은 미확인이다. | 위치는 그리되 ●/○ 중 하나를 억지로 선택하지 않는다. 미확인임을 구별한다. |
| C가 질적 영역으로 알려져 있다. | 영역 또는 글로 보여주며 숫자 상세를 만들어내지 않는다. |
| 중심 정보는 없고 발 정보만 있다. | 발은 그린다. C는 생략하고 미확인을 안내한다. |
| 적용 범위가 묶음이다. | ‘左掤 전체’ 또는 ‘左掤 1–3동작’처럼 범위를 표시한다. 매 동작마다 별개 용법으로 재작성하지 않는다. |
| 전투 가정이 미작성이다. | 미작성과 비적용을 구분한다. ‘전투적 의미가 없다’고 단정하지 않는다. |
| 접촉 또는 회전이 추론이다. | 해설의 추론 표시를 유지한다. 실제 접촉·회전 기호로 자동 변환하지 않는다. |
| 참조가 깨져 있다. | 작성자에게 오류를 보고한다. 해당 정보만 사용할 수 없다고 표시한다. |

상단의 단·자세 선택, 고정 좌표판, 독립 스크롤 설명, 하단 이전·다음은 유지한다. 설명 순서도 ‘어떻게 → 왜 → 음양 → 전투 가정 → 자세 확인’을 기본으로 한다. 긴 묶음 해설과 근거는 접어볼 수 있게 하되 실제 사용성은 UI 단계에서 검증한다. 데이터 항목을 모두 별도 카드로 만들 필요는 없다.

시작 상태와 중간 상태는 동작 진행률에 더하지 않는다. 현재 합의한 자세 경계의 시작 화면은 유지한다. 연속 연습에서 이 화면을 건너뛰는 모드는 이번 범위에 넣지 않는다.

## 11. 최소 예시

다음은 저장 형태를 설명하기 위한 조각이며 실제 권가 데이터가 아니다.

```json
{
  "id": "example-right-foot-position",
  "position": {
    "status": "known",
    "value": {"x": 1, "y": 0},
    "basis": "illustration",
    "precision": "approximate",
    "evidence": [],
    "note": "모델 설계용 예시이며 실연을 관찰한 좌표가 아니다."
  },
  "groundContact": {"status": "unknown", "reason": "unrecorded"}
}
```

발의 위치가 알려져도 접촉은 미확인일 수 있다. 다른 예로 C는 `{kind:"region", anchor:"rightFoot"}`라는 값을 가진 Claim으로 나타낼 수 있다. 이것만으로 양발 체중 비율이나 지면 반력, 압력중심을 계산하지 않는다.

## 12. 검증 규칙

구조 검증은 다음을 확인해야 한다.

- ID 중복, 깨진 참조, 잘못된 소속, 순환 시작 참조를 거부한다.
- 이전 자세는 같은 권가 순서의 바로 앞 자세여야 한다.
- 시작·중간·끝 사이의 좌표계가 다르면 비교나 경로를 조용히 그리지 않는다.
- 중간 상태 ID를 공식 동작 수에 더하지 않는다.
- `before` 관계의 순환이나 자기 참조를 거부한다. 배열 순서에서 시간 관계를 발명하지 않는다.
- known Claim에는 값과 근거 유형이 있어야 한다. unknown에는 임의의 값이 들어가면 안 된다.
- source/observation에는 유효한 근거 ID와 위치가 있어야 한다. 접촉 기호에는 명시적 지지가 필요하다.
- 사건의 범위와 해석의 대상은 실제 소속 동작 안에서 유효해야 한다.
- 양발의 역할을 무조건 반대로 만들지 않는다. 미확인을 고정값으로 대체하지 않는다.

구조가 통과해도 실제 태극권 동작이 맞다는 뜻은 아니다. 사부님·자료와의 대조는 별도 검토이다. 모든 상태의 C가 특정 영역 안에 있어야 한다는 식의 단순 규칙으로 실제 동작을 합격·불합격 판정하지 않는다.

[설계 시험](design-tests/model-contract.test.mjs)은 이 중 핵심 참조·표시 규칙을 작은 가상 데이터로 확인한다. 전체 스키마 검사기나 실제 화면 테스트를 대신하지 않는다.

## 13. 이행 순서와 보류 범위

먼저 이 설계를 바탕으로 실제 저장 형식과 검증기를 만든다. 작은 정적 사이트를 유지하며 서버·데이터베이스·새 UI 프레임워크를 전제하지 않는다. JSON으로 표현 가능한 레코드를 사용하되 현재처럼 HTML을 직접 여는 사용 방식은 유지할 수 있는지 확인한다. 파일 분리나 로딩 방식 변경은 별도 실행 검증 후 결정한다.

이행은 다음 순서로 진행한다.

1. 좌표계 문서의 축·발 기준점·상태/사건 구분을 이번 결정과 맞춘다.
2. 이 문서의 필드를 실행 가능한 스키마와 검증기로 옮긴다.
3. 예비식의 기존 네 동작을 출처·근사·미확인으로 다시 분류한다.
4. 새 데이터를 기존 화면이 읽도록 연결하고 전후 화면을 비교한다.
5. 시작 상태와 부분 미등록을 처리한다.
6. 음양·전투 가정의 작성 원칙을 확정하고 실제 콘텐츠를 넣는다.
7. 太極起勢에서 팔·높이·정지한 발의 변화를 검증한 뒤 攬雀尾로 확장한다.

기존 `cx`, 화살표 기울기, 픽셀 오프셋을 새 수련 사실로 옮기지 않는 일이 특히 중요하다. 화면을 이전과 완전히 같게 유지하는 것보다 정보의 의미를 보존하는 것이 우선이다. 달라지는 표현은 회귀 기록에 이유를 남긴다.

첫 버전에서는 정밀 3차원 골격, 접촉력 계산, 자동 용법 생성, 연속 애니메이션, 상대 물리 시뮬레이션, 범용 운동 온톨로지를 만들지 않는다. 당장 입력하고 검토할 수 있는 정보만 구조화한다.

## 14. 이번 단계의 완료와 미완료

현재 모델 한계 분석, 상태·동작·해석 분리, 필드별 근거와 미확인 규칙, UI 계약을 설계했다. 2026-09-23에 로컬 Node.js 환경에서 `node docs/design-tests/model-contract.test.mjs`를 실행했고 가상 데이터의 핵심 계약 시험 20개가 통과했다. 이 시험은 전체 필드의 검증이나 브라우저 실행을 포함하지 않는다.

예비식 실제 데이터 변환, 좌표계 문서 이행, 전체 실행 스키마, 배포 UI, 사부님 지도와의 기술 검증은 아직 완료하지 않았다. 설계 시험 통과를 이 항목들의 완료로 기록하지 않는다.
