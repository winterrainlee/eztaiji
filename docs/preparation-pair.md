# 예비식으로 만든 수련 원본·배포 데이터 쌍

작성일은 2026-09-23이다. 실제 이전 대상으로 기존 eztaiji의 預備式 4동작을 사용했다. 가상의 태극권 동작을 실제 수련 원본에 넣지 않았다. 다만 기존 설명의 원문 대조와 사부님 확인이 끝난 것은 아니므로 **이전 후보**로 기록한다.

## 1. 이번에 실행한 범위

- [x] `training/datasets/yijian.json`에 예비식 시작 상태와 4동작을 기록했다.
- [x] 수련 원본과 배포 결과에 각각 적용할 실행 스키마를 만들었다.
- [x] 원본을 바꾸지 않는 Node 변환 함수와 참조 검사를 작성했다.
- [x] 로컬에서 원본 검사 → 변환 → 결과 검사 → 의미 보존 대조를 실행했다.
- [x] `.build/preparation/`에 검사한 배포 JSON·데이터 스크립트·보고서를 생성했다.
- [x] Node 시험 21개와 JSON Schema 관련 시험 14개, 총 35개를 실행해 통과했다.
- [ ] 외부 권보 원문을 다시 읽고 기존 설명 및 접촉 정보를 대조한다.
- [ ] 화면에 새 배포 데이터를 연결하고 실제 표시를 검증한다.
- [ ] 전체 사이트 빌드, 실패 시 배포 차단, Pages 게시 설정을 연결한다.

현재 루트 HTML·catalog.js·Pages 설정은 바꾸지 않았다. 기존 사이트는 여전히 이전 데이터로 동작한다. `training/`의 수정이 운영 화면에 자동 반영되는 상태는 아니다.

## 2. 파일과 책임

| 파일 | 역할 |
| --- | --- |
| `training/datasets/yijian.json` | 사람이 검토하고 고칠 수련 원본이다. 예비식만 포함한 부분 Dataset이다. |
| `schemas/training.schema.json` | 원본의 필드와 지원 범위를 검사한다. |
| `schemas/deployment.schema.json` | 읽기용 결과의 필드와 지원 범위를 검사한다. |
| `schemas/common.schema.json` | 양쪽이 공유하는 Claim·상태 값의 의미를 검사한다. |
| `scripts/compile-data.mjs` | 입력 객체에서 읽기용 객체를 만드는 Node 변환기다. 파일이나 브라우저를 조작하지 않는다. |
| `scripts/check_preparation_pair.py` | 표준 JSON Schema 검사를 변환 전후에 실행하는 로컬 시범 도구다. |
| `tests/preparation-pair.test.mjs` | 참조·보존·직렬화 규칙을 시험한다. |
| `tests/test_preparation_schemas.py` | 정상·잘못된 형식과 미확인 처리를 시험한다. |
| `.build/preparation/deployment.json` | 검사 후 자동 생성한 읽기용 데이터다. Git에 넣거나 손으로 편집하지 않는다. |
| `.build/preparation/taiji-data.js` | 같은 결과를 데이터 초기화용 스크립트로 직렬화한다. |
| `.build/preparation/report.json` | 이번 생성의 검사 결과와 입력 해시를 기록한다. |

`dist/`는 만들지 않는다. 아직 화면 파일을 조립하지 않았으므로 데이터만 있는 폴더를 완성된 사이트로 취급하지 않는다. 이번 생성물은 로컬에서 쌍을 비교하기 위한 예시이며, 배포용 형식이라는 말이 실제 게시 완료를 뜻하지 않는다.

## 3. 시작 상태와 4동작

`p001-start`는 권가 시작 전의 별도 상태다. 기존 1동작 결과를 복사하지 않았다. 근거가 없는 발 위치·허실·접촉·C·B는 미확인으로 두었다.

기존 네 동작의 제목, 동작 설명, 원리 설명과 확인 문구를 옮겼다. 현재 확인되는 근거는 이전 웹앱 기록이므로 원문 확인 완료 표시를 붙이지 않는다.

| 화면 | 기존 설명에서 옮긴 흐름 | 새 데이터의 처리 |
| --- | --- | --- |
| 시작 상태 | 1동작 전의 상태다. | 미확인 신체 정보를 채우지 않는다. |
| 1동작 | 오른다리가 받치고 왼발을 비운다. | 들기 사건과 결과 상태를 분리한다. |
| 2동작 | 빈 왼발을 왼쪽에 놓는다. | 발 위치와 지지 역할을 별도로 기록한다. |
| 3동작 | 왼발을 정렬하며 지지를 옮긴다. | 뒤꿈치 내림을 뒤꿈치부터 착지하기로 바꾸지 않는다. |
| 4동작 | 왼다리 지지 아래 오른발을 정렬한다. | 오른발 접촉점·회전축을 새로 추정하지 않는다. |

이 표는 기존 코드의 설명을 요약한 것이며 외부 권보를 새로 검증한 결과가 아니다. 5개의 화면 상태를 사용하지만 번호가 붙은 동작은 계속 4개다.

## 4. 근거와 의미를 처리한 방식

기준 기록은 [기존 index.html](https://github.com/winterrainlee/eztaiji/blob/ba53fbbb5d562efeb36bc96707baebf6814acd3d/index.html)의 `preparation`과 `draw()`다. 예전에 참고했던 [외부 권보](https://tsaitaiji.blogspot.com/2024/03/1-64.html)는 이번 조회에서 접속 제한이 발생했고 검색 결과로도 예비식 문단을 재확인하지 못했다. 따라서 접근한 적 없는 원문을 다시 확인한 것처럼 출처를 붙이지 않았다.

이전 코드의 발 좌표는 새 기준점의 **설명용 근사 배치**로만 옮겼다. `lt/rt`의 화면 기울기는 실제 각도가 아니라 방향 범주로 표현했다. B 정면 표기도 설명용 도해이며 실제 회전량이 0이라는 증거는 아니다.

C는 기존 화면에서 가리킨 발 쪽을 질적 영역으로 옮겼다. 원래의 `cx` 값과 화면 오프셋은 `authoring.legacyRendering`에 대조용으로 남기고 배포 상태의 물리 좌표에는 넣지 않는다.

기존 접촉·뒤꿈치 설명은 안내와 사건의 추론 표시에 보존했다. 확정 접촉 상태는 `unknown/unverified`로 두었다. 변환기는 직접 확인한 문헌·관찰 근거가 없는 Toe/Heel 기호를 생성하지 않는다. **이전 코드에 문장이 존재한다는 사실과 그 문장이 실제 동작에 맞는다는 확인을 구분한다.**

음양은 기존 지지·비움 관계를 읽는 프로젝트 해석으로 4개 작성했다. 좌우에 陰陽을 고정한 분류가 아니다. 전투 가정은 자세 전체의 `pending` 기록으로 남겼다. ‘전투적 의미 없음’으로 바꾸거나 독립 용법을 발명하지 않았다.

## 5. 수련 원본과 배포 결과의 차이

원본에는 몸 상태, 움직임, 해석, 근거, 이전 기록의 대조 메모를 각각 둔다. 배포 결과에는 같은 의미를 유지하면서 다음을 미리 연결한다.

- 화면 순서와 이전·다음 ID를 만든다.
- 시작·결과 상태 ID와 해당 화면의 원리·음양·전투 해설 ID를 연결한다.
- 확인된 근거에 따라 접촉·사건 기호의 표시 자격을 계산한다.
- 근거의 공개용 제목·URL·설명만 남기고 작성용 Source.location과 authoring은 제외한다.

상태는 ID별로 한 번 저장한다. 다음 자세의 시작 화면이 생기면 직전 결과 상태 ID를 공유하되 이전 사건·설명까지 복사하지 않는다. 이번 실제 원본은 예비식만 포함하므로, 이 연결은 **TEST ONLY라는 가상 다음 자세를 사용하는 시험 코드에서만** 확인했다. 太極起勢를 작성한 것으로 세지 않는다.

원본과 배포본 모두 미확인·근사·추론·설명용 예시라는 성격을 유지한다. 픽셀 좌표, 화면 크기, 스크롤 상태는 배포 데이터에 넣지 않는다. 결과물의 목적은 무조건 작은 파일을 만드는 것이 아니라 브라우저가 자료를 다시 해석하지 않고 읽게 만드는 것이다.

## 6. 이번 스키마의 한계

이번 실행 계약은 `0.1.0 / preparation-pilot`이다. 전체 데이터 모델 0.1의 모든 기능을 구현했다고 표시하지 않는다.

한 동작·한 자세의 해석, 상태·사건, 필드별 Claim, 출처, 미등록 결과, 이전 자세 결과 참조를 다룬다. 동작 묶음, 중간 상태, 사건 선후 관계, 충돌 후보값 목록은 아직 지원하지 않는다. 해당 필드를 넣으면 오류로 알려주며 조용히 버리지 않는다. 예비식 숫자에 맞춰 4동작만 허용하는 스키마는 아니지만, 다음 자세에 쓰기 전 그 자세가 요구하는 기능을 확장·시험해야 한다.

원본과 결과에 별도의 스키마가 있으며 공통 의미를 가진 값만 common.schema.json을 공유한다. `$id`는 규격 식별자다. 검사는 로컬에 등록한 스키마만 사용하고 웹을 조회하지 않는다.

표준 스키마 검사는 개발용 Python jsonschema로 실행했고 변환 자체는 Node 순수 함수다. 운영 사이트의 기술 구성을 Python으로 바꾼 것은 아니다. 예정된 `node scripts/build.mjs` 전체 명령은 아직 없다. Node 변환기를 단독 호출하면 전체 JSON Schema 검사를 대신하지 않으므로 게시 경로로 사용해서는 안 된다.

## 7. 재현 명령

Node와 Python이 있는 개발 환경에서 다음을 실행한다. 이번 실행 환경에는 jsonschema 4.26.0이 설치되어 있었다. 운영 배포용 의존성 잠금과 실행 환경 고정은 아직 별도 작업이다.

```sh
python -m pip install -r requirements-dev.txt
node --test tests/preparation-pair.test.mjs
python -m unittest discover -s tests -p 'test_preparation_schemas.py' -v
python scripts/check_preparation_pair.py --emit
```

마지막 명령은 표준 원본 검사, Node 참조 검사·변환, 표준 결과 검사, 필드별 보존 대조와 재생성 비교 후 `.build/preparation/`에 예시를 쓴다. 입력 JSON의 중복 키와 NaN도 거부한다.

검사 결과는 1자세·4동작·5화면이며 Node 21개와 스키마 관련 14개 시험이 통과했다. 기존 설계 시험 20개를 이번 시험 수에 더하지 않았다. 실제 브라우저, 모바일 표시, file:// 로딩, Pages 배포와 기술 내용의 타당성을 확인한 것은 아니다.

## 8. 다음 검토

먼저 이 예비식 쌍에서 작성량·공개 표시·미확인 처리의 적절함을 검토한다. 이어 원문 접촉 근거를 재대조하고 화면 연결 또는 전체 빌드 명령을 구현한다. 현 단계에서 전체 권가 스키마나 운영 배포 검증까지 완료로 표시하지 않는다.
