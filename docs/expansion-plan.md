# eztaiji 확장 계획

- 목적: eztaiji를 단순한 자세 도해가 아니라, **좌표 → 신체 물리 → 음양 → 무술적 의미**를 함께 읽는 개인 수련 도구로 확장한다.
- 진행 원칙: 한 번에 많은 기능을 넣지 않고, 아래 항목을 하나씩 구현·검증한 뒤 체크한다.
- 기준: 실제 수련과 사부님의 지도를 우선하고, 자료에서 확인되지 않은 내용은 추론이나 예시임을 명확히 표시한다.

## 1. 시작 상태 개념 정의

목표: `0동작`이라는 표현 대신, 각 자세의 **시작 상태**를 명시한다.

### 원칙

- 시작 상태는 새로운 동작 번호가 아니다.
- 일반적으로 `이전 자세의 마지막 상태 = 다음 자세의 시작 상태`로 본다.
- 첫 자세인 預備式만 이전 자세를 참조하지 않고 `권가 시작 전 상태`를 별도로 가진다.
- UI에는 `0동작`이 아니라 `시작 상태`라고 표시한다.
- 필요하면 설명에 `이전 자세 ○○의 마지막 상태`라고 덧붙인다.

### 체크

- [x] `coordinate-system.md`에 시작 상태 정의를 추가한다.
- [x] `routine-navigation.md`에 탐색 규칙을 추가한다.
- [x] 첫 자세의 초기 상태를 어떻게 표현할지 확정한다. — `권가 시작 전 상태`로 표시하고 확인된 값만 기록한다.
- [x] 이후 자세가 이전 자세의 마지막 상태를 참조하는 규칙을 확정한다. — 같은 물리 상태를 새 자세의 출발점으로 참조한다.

## 2. 범용 동작·상태 데이터 구조 설계

목표: 預備式 전용 데이터 구조를 전체 64자세에 사용할 수 있는 구조로 바꾼다.

설계 기준은 [동작·상태 데이터 모델 0.1](data-model.md)이다. 기존의 한 프레임에 모든 정보를 넣는 개념도는 아래처럼 갱신한다. 이번 문서화와 설계 시험은 실제 데이터 변환이나 UI 구현의 완료를 뜻하지 않는다.

### 필요한 정보

가능한 범위에서 다음 정보를 서로 구분해 기록한다.

- 상태에는 왼발·오른발 위치 `(x, y)`, 발별 허실·지지 역할, 발끝 방향과 현재 접촉을 담는다.
- 상태에는 중심 `C`의 점 또는 질적 영역, 몸 방향 `B`, 필요한 팔의 상대적 배치를 담는다.
- 동작에는 뒤꿈치 들기·내리기, 중심 이동, 회전 `ΔB` 같은 변화와 확인된 선후 관계를 담는다.
- 안내에는 동작 설명과 자기 점검 항목을 담는다.
- 해석에는 원리·음양·전투 가정과 적용 범위를 담는다.
- 각 정보에는 근거 유형, 위치, 근사 여부와 미확인을 구분해 기록한다.

### 개념 구조

```text
Dataset
  sections -> posture occurrences -> numbered motions
  coordinateFrames
  states
  interpretations
  sources

PostureOccurrence
  id, name
  start: initial / previousEnd
  motionIds[]
  introduction

Motion
  id, number
  endStateId
  checkpointStateIds[]
  events[], eventRelations[]
  instruction, checks[]

State
  id, coordinateFrameId
  feet.left / feet.right
  center
  body
  arms

Interpretation
  category: principle / yinYang / application
  scope: motion / group / posture
  availability
  content / reason

Claim
  value + basis + precision + evidence
  또는 unknown / not_applicable
```

### 체크

- [x] 현재 `lx / lt / rt / cx / shi` 구조의 한계를 정리한다.
- [x] 새 프레임 스키마를 문서로 정의한다. — `data-model.md` 0.1에 상태·동작·해석을 분리했다.
- [x] 모르는 값과 미등록 참조를 구분하는 규칙을 정한다. — 물리 필드는 Claim의 미확인으로, 미등록 결과 참조는 `null`로 표시한다.
- [x] 관찰값과 추론값을 구분하는 필드를 정한다. — 필드별 근거와 근사 여부를 기록한다.
- [x] 시작 상태·중간 상태·부분 미등록과 UI의 연결 규칙을 정의한다.
- [x] 가상 데이터로 핵심 설계 계약을 시험한다. — 로컬 Node.js에서 20개 시험을 통과했다. 전체 스키마·실제 권가·브라우저 검증은 아니다.
- [x] 좌표계 문서의 고정 축, 발 기준점, 상태와 사건의 구분을 새 설계와 맞춘다. — `coordinate-system.md` 1.3에 반영하고 `data-model.md`의 이행 상태를 맞췄다. 코드·실제 데이터 이행은 별도다.
- [ ] 실행 가능한 전체 데이터 스키마와 검증기를 작성한다.
- [ ] 기존 預備式 4동작을 새 구조로 변환한다.

## 3. 음양 해석 원칙 만들기

목표: 음양을 단순한 좌우 대응이 아니라, 동작 안에서 실제로 변하는 관계로 설명한다.

### 원칙

- `왼쪽 = 陰 / 오른쪽 = 陽`처럼 고정하지 않는다.
- 해당 동작에서 실제로 드러나는 관계만 적는다.
- 모든 프레임에 억지로 음양 항목을 넣지 않는다.
- 하나의 프레임에 여러 음양 관계가 동시에 존재할 수 있다.

### 예시 관계

- `虛 ↔ 實`
- `開 ↔ 合`
- `進 ↔ 退`
- `收 ↔ 放`
- `상대의 進 ↔ 나의 化`
- `한쪽 공간을 비움 ↔ 다른 쪽 공간을 차지함`

위 예시에는 전통적 대립쌍과 프로젝트의 설명용 대비가 함께 있다. 작성 원칙에서 둘을 구분하며, 모든 대비를 표준 음양 분류로 단정하지 않는다.

### 체크

- [ ] 음양 해석 원칙을 별도 문서에 정의한다.
- [ ] 한 프레임에 여러 관계를 저장하는 형식을 정한다.
- [ ] 음양이 불분명한 경우 비워 두는 원칙을 명시한다.
- [ ] 預備式에서 실제로 유효한 음양 관계만 시험 입력한다.

## 4. 전투 가정 해석 원칙 만들기

목표: 동작을 고정된 공격·방어 기술로 단정하지 않고, 상대와의 힘 관계 속에서 이해한다.

### 기본 구조

```text
상황
상대가 어떤 힘을 주는가?

대응
그 힘에 대해 내 몸 전체가 어떻게 반응하는가?

결과
힘·중심·공간의 관계가 어떻게 바뀔 수 있는가?

한계
어떤 전제에서 가능한 설명이며 무엇이 아직 확인되지 않았는가?
```

### 원칙

- 손 모양만 보고 공격·방어를 단정하지 않는다.
- 독립된 전투 용법이 아니라 다음 동작을 위한 구조 형성일 수 있다.
- 한 프레임이 아니라 여러 동작 묶음 전체가 하나의 용법일 수 있다.
- 사부님 설명, 문헌, 외부 영상, 프로젝트 해석을 구분한다.

### 범위

- `motion`: 한 동작 자체에서 의미가 충분히 드러남.
- `group`: 左掤 등 여러 동작 묶음에 걸쳐 의미가 완성됨. 일부에만 해당하면 대상 동작 ID를 명시한다.
- `posture`: 한 자세 전체를 봐야 의미를 설명할 수 있음.

### 체크

- [ ] 전투 가정 작성 규칙을 문서화한다.
- [ ] `scope: motion / group / posture` 규칙을 확정한다.
- [ ] 독립 용법이 없는 동작의 표기 방식을 정한다.
- [ ] 출처와 추론을 구분하는 규칙을 확정한다.
- [ ] 預備式에는 억지 용법을 붙이지 않고 준비 구조로 설명 가능한지 검토한다.

### 설명 영역 순서

1. **지금 어떻게 움직이나**

- 여러 동작에 걸친 설명은 범위를 명시한다.
- 출처가 필요한 해석은 근거를 접어 볼 수 있게 한다.
